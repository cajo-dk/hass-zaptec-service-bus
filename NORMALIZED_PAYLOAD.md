# Normalized Zaptec Payload

Schedule observations 761, 762 and 763 are now preserved as `time_zone`,
`time_schedule` and `next_schedule_event`, respectively. They retain their
original parsed types; these are not normalized start/stop timestamps.
An empty observation for 762/763 clears the prior value to JSON `null`.
These optional fields are absent until first observed.

This document describes the normalized JSON object published by the monitor after receiving Zaptec Azure Service Bus messages.

Source implementation:

- [zaptec_charge_monitor.py](/c:/Users/AlexRasmussen/src/zaptec/zaptec_charge_monitor.py)

## Output topic

The normalized object is published to:

```text
<mqtt_base_topic>/chargers/<sanitized_charger_id>/state
```

With the default configuration, that becomes:

```text
zaptec/chargers/<sanitized_charger_id>/state
```

## Top-level fields

These fields are always part of the normalized object:

| Field | Type | Description |
| --- | --- | --- |
| `state` | `string` | Charger state derived from `StateId = 710`. |
| `device_id` | `string` | `DeviceId` from the incoming message, or `charger_id` if missing. |
| `charger_id` | `string` | `ChargerId` from the incoming message, or `DeviceId`, or `"unknown"`. |
| `state_710_raw` | `number` | Raw numeric operation mode from `StateId = 710`. |
| `total_energy` | `number` | Extracted from `StateId = 554` OCMF meter data when available. |
| `last_state_id` | `number \| string \| null` | Most recent incoming `StateId` after parsing. |
| `last_message_timestamp` | `string \| number \| null` | Original `Timestamp` value from the last processed message. |
| `last_updated_utc` | `string` | UTC timestamp generated by the monitor when it publishes the payload. |

## State normalization

`state` is derived from `StateId = 710` using this mapping:

| Raw value | Normalized `state` |
| --- | --- |
| `1` | `disconnected` |
| `2` | `connected_requesting_charge` |
| `3` | `charging` |
| `5` | `connected_finished_idle` |

If an unknown operation mode is received, the monitor publishes:

```text
unknown_<raw_value>
```

Example:

```json
{
  "state": "unknown_9"
}
```

## Special normalization rules

### `StateId = 554`

`signed_meter_value` stores the parsed incoming value. If the payload contains OCMF data, the monitor also extracts:

```json
{
  "total_energy": "<RD[0].RV>"
}
```

Supported forms:

- JSON object with `RD[0].RV`
- String prefixed with `OCMF|` followed by JSON

### Forced zero values when not charging

When `state_710_raw != 3`, these fields are forced to `0`:

- `total_charge_power`
- `voltage_phase_1`
- `voltage_phase_2`
- `voltage_phase_3`
- `current_phase_1`
- `current_phase_2`
- `current_phase_3`

## Timestamp handling

Incoming `Timestamp` values are used to prevent stale updates from overwriting newer cached values.

Accepted forms:

- ISO 8601 string
- Epoch seconds
- Epoch milliseconds

If a field update arrives with an older timestamp than the cached value for that field, it is ignored.
